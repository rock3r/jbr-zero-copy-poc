1. Goal

Expose one stable abstraction across all headed JBR platforms:

“For display D, call me roughly once per refresh with a monotonic timestamp, on a non-EDT thread, without blocking the compositor or AWT.”

Clients (later: CMP / Skiko) decide when to paint. JBR never calls repaint(), never tracks dirty state, never knows about Compose or Skia interop.

Success criteria

  • JBR.getFramePacing() works the same way on macOS, Windows, and Linux.
  • Backend quality is queryable — clients can refuse weak clocks.
  • Zero cost when unused — no tick threads / display links until the first subscriber.
  • Independent of JBRSkia / zero-copy / command ABI.
  • Phase 2 can consume the API without forcing a v2 redesign.

Why not timer-only?

Timer-based limiters (FrameLimiter, Swing Timer) are good rate governors but inherently jittery as a phase-locked cadence (OS timer granularity, scheduler, wrong refresh rate). This API exists so clients can get a real (or composition-aligned) tick when the OS provides one, with an estimated timer only as the honest weak tier.

3. Public API (jbr-api)

New @Service in the standalone jbr-api jar, following existing patterns (JBR.getFramePacing() / JBR.isFramePacingSupported()). Names are bikesheddable; the shape matters. 

package com.jetbrains;

/**
 * Display-aligned frame pacing clock.
 * Delivers asynchronous ticks for rate-limiting UI work.
 * Not a present-completion or drawable callback.
 * Listeners must return immediately and must not enter AWT locks.
 */
@Service @Provided
public interface FramePacing {

    enum Quality {
        /** True display link (e.g. CVDisplayLink). */
        DISPLAY_LINK,
        /** OS composition / vblank-aligned clock — not glass present time. */
        COMPOSITION_CLOCK,
        /** Best-effort high-res timer at estimated refresh rate. */
        ESTIMATED,
        NONE
    }

    Quality getQuality();

    /** Opaque stable id for the screen of {@code gc}, or -1 if unknown. */
    long displayId(GraphicsConfiguration gc);

    /** Nominal period in ns, or 0 if unknown. Advisory only. */
    long refreshPeriodNanos(long displayId);

    /** @return subscription, or null if that display cannot be paced */
    Subscription subscribe(long displayId, Listener listener);

    @Provides
    interface Listener {
        /** Non-EDT thread. timeNanos is monotonic, for interval math. */
        void onTick(long displayId, long timeNanos);
    }

    @Provided
    interface Subscription extends AutoCloseable {
        long displayId();
        @Override void close(); // idempotent
    }
}

API rules

Availability

  • getFramePacing() non-null when any backend exists at quality ≥ ESTIMATED
  • null on non-JBR, headless, or hard failure

Listener contract

  • Return immediately
  • No AWT painting, no invokeAndWait, no RenderQueue
  • May invokeLater (client choice)

Multi-subscriber

  • N listeners per displayId
  • One native clock per display (refcount)

Hotplug / sleep

  • Display gone → stop ticks for that id
  • Client re-resolves displayId(gc) after config change
  • JBR does not track windows

What this is not

  • Not present-timestamp / CAMetalDrawable completion
  • Not a replacement for heavyweight Skiko MetalRedrawer vsync
  • Not Java2D BufferStrategy vsync
  • Not tied to JBRSkia.ScopedSkiaCanvas

Optional extension (can wait)

long sourceGeneration(long displayId) — bumps on mode change / wake so clients can drop coalesced permits. Nice for Phase 2; not required for v1.

4.1 macOS

Decision to lock in J0:

OptionProsCons
A. FramePacing-owned CVDisplayLink (recommended) Clear ownership; works without Java2D Metal traffic; no KEEP_ALIVE idle stop coupling Possible dual-link if Metal blit link also runs
B. Piggyback MTLContext link One link per display; less power when both active Coupled to blit keep-alive; idle link stops hurt pure Compose animation

displayId: CGDirectDisplayID zero-extended to long, mapped from GraphicsConfiguration via existing AWT paths.

4.2 Windows

Reject: DwmFlush as production tick

PoC measurements: in the live process DwmFlush can return S_OK yet block ~250 ms (~4 Hz) because it waits for DWM to compose frames that include this process’s presents — a feedback stall when the client gates presents on the same tick.

  • Accept: read DWM composition timing → wait to next vblank boundary with high-res waitable timer.
  • Daemon thread, AttachCurrentThreadAsDaemon, JNI onTick.
  • DWM off / remote → fall back to ESTIMATED timer.
  • displayId: HMONITOR or stable device-name hash round-tripping with GC.
  • v1 multi-monitor: prefer per-HMONITOR threads if cheap; primary-only cadence is acceptable if documented.

4.3 Linux

Design for graceful degradation, not perfection. Linux v1 ships with ESTIMATED; better backends are quality upgrades behind the same API.

  1. Resolve refresh: XRR / Wayland output mode / DisplayMode.
  2. Thread: clock_nanosleep / waitable timer aligned to period → ESTIMATED.
  3. Optional: X11 + GLX glXGetVideoSyncSGI / wait → upgrade to COMPOSITION_CLOCK if safe.
  4. Wayland: do not invent a dummy wl_surface just for ticks in v1.

5. Internal architecture

jbr-api: com.jetbrains.FramePacing │ ▼ share/.../FramePacingService.java @Service create(), quality, displayId, subscribe │ ┌────┼────────────────────┐ ▼ ▼ ▼ macos/ windows/ unix/ FramePacingMac.mm FramePacingWin.cpp FramePacingLinux.c CVDisplayLink DWM timing thread timer / optional GLX │ │ │ └────┴────────────────────┘ │ shared multi-subscriber registry displayId → list<Listener global refs>

Shared responsibilities

Java

  • Listener list + generation tokens
  • Refcount start/stop native clock
  • Exception clearing around callbacks
  • displayId(GraphicsConfiguration) via toolkit peers

Native

  • Daemon attach with stable name JBR-FramePacing
  • Never block waiting for Java
  • Clear pending JNI exceptions after each listener

Do not put this under JBRSkiaService / JBRSkiaInterop.* or behind sun.java2d.skia.interop.* flags.

9. Non-goals (this program)

  • CMP SwingRepaintPacer, Skiko permit/watchdog, Jewel flags
  • Command interop / zero-copy / JBRSkia ABI
  • Present timestamps / “frame actually on glass”
  • Replacing Skiko heavyweight redrawer vsync
  • Guaranteeing tear-free Swing blits
  • Perfect Wayland presentation-time in v1

10. Phase 2 expectations (not this plan’s work)

When J0–J5 land, CMP/Skiko only need:

  1. JBR.getFramePacing()
  2. displayId(component.graphicsConfiguration)
  3. subscribe while dirty / animating
  4. Coalesce one repaint per tick
  5. Timer fallback if null / quality too low / watchdog miss
CMP SwingRepaintPacer dirty + coalesce + timer fallback + mode flag │ subscribe / onTick ▼ Skiko thin adapter (optional) GC → displayId · Subscription lifecycle │ JBR.getFramePacing() ▼ jbr-api FramePacing ← this program │ macOS DL · Win composition · Linux estimated
